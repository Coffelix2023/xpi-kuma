# plan.md — wireframe (kuma-dashboard)

> 本阶段唯一需求事实来源。每轮深挖后**覆写本文件**，不新建副本。

## 1. 目的 (Why)

扩展 xpi-kuma 现有 Glimpse 监控面板的信息架构，把「用量归因」提上来：看得出哪个项目
(cwd) / 会话 / 模型最烧钱。这个原型回答的问题是「钱花在哪了」。

## 2. 受众 (Who)

- 主要：xpi-kuma 开源用户。各自跑 Pi，配置各异，数据量从 0 开始。
- 约束后果：零配置可用，无数据不空白，不假设用户已配预算或已有历史数据。

## 3. 范围

### 包含

- 用量归因维度：项目(cwd) / 会话 / 供应商·模型，可切换
- 信息架构重构：花费概览 → 用量归因 → 供应商健康 → 趋势
- 零数据引导态（首次运行 / 记录被 retention 清理 / 未配置供应商共用同一引导视图）
- 周期切换沿用 `1h / 24h / 7d / 30d`

### 不包含

- 预算与告警（阈值、超支预测）—— 本轮明确去掉，用户第 3 轮追认
- 面板内写盘（改 `config.yaml`）；预算/配置修改本轮不做
- 供应商详情下钻页（本页保持只读 + 行内刷新）；账户页是独立页面阶段 `pages/accounts/`，不在此阶段目录内
- 供应商健康块的卡片形态（第 2 轮已改为行列表 + 指示灯，不再回退）
- 全 down 降级态、sqlite 错误态（用户只勾了「零数据引导态」，本轮不给位置）
- 图表去 CDN（保持 Chart.js CDN，离线时降级隐藏）

## 4. 页面清单

| ID | 页面 | 优先级 | 状态覆盖 |
| :--- | :--- | :--- | :--- |
| P1 | 主面板（花费概览 / 归因 / 供应商 / 趋势） | P0 | main |
| P2 | 零数据引导态 | P0 | empty |
| P3 | 供应商账户（独立阶段 `pages/accounts/`） | P0 | main / empty |

> ID 规范：两位数字前缀 + kebab-case，决定导航与文件排序。
> P2 是 P1 的状态屏，不是独立产品页；拆成独立文件是为了状态覆盖可评审。

## 5. 交付形态

- [x] desktop 1280（对齐 Glimpse 窗口 1200x800 的可用宽度）
- [ ] mobile 390 —— 本轮不做（面板是桌面原生窗口，无移动端场景）
- [x] 状态覆盖：main / empty（loading、error 本轮不做，见 §3 不包含）

## 6. 主题与语言

- 配色来源：`<项目根>/THEMES.md`（shadcn token）
- wireframe 仅取基础 token：`background / foreground / border / muted`，不增加线框工作量
- 主题：默认暗色，页内可切换 亮/暗
- 语言：默认 `zh-CN`，页内可切换 `zh-CN` / `en`
- 已知张力：repo 根 `DESIGN.md` 是 Terminal Minimalist(hex)，实装 `src/ui/dashboard-css.ts` 用
  `--kuma-*` 变量。原型按硬规则只消费 `THEMES.md`；将来落地到代码需要一次 token 映射，
  本计划不做。

## 8. 任务编排

> 任务清单与进度在同目录 `tasks.md`（checkbox 状态机），本文件不重复维护清单。

切分理由：

- 先骨架后填充，遵循 SKILL.md §7 骨架优先；`1.1` 用 `write`，其余全是 `replace` / `insert`。
- 顺序 = 首屏视觉层级顺序（概览 → 归因 → 供应商 → 趋势），因此评审时从上往下读即有层次感。
- `1.7` 独立于 `1.3~1.6`：空态是另一个文件，可与主面板并行，但本轮串行执行以免锚点混乱。
- `1.8` 收尾：块优先级与语义 ID 必须最后统一核对，否则前面每步都要回改。
