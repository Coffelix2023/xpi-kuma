## Context

当前系统已经将真实 `message_end` usage 写入 SQLite，并由 API 聚合 provider/model、项目归因和趋势；供应商 probe 另有 TTFT 与总响应时间数据。现有面板以总览、统计、趋势和供应商区域为主，生产代码使用 TypeScript、原生 DOM、SQLite 和内置样式 token，页面不能依赖外部资源。具体行为契约见 `specs/` 下的新增与修改 delta。

本设计把 probe 健康度与真实调用效率分开：probe 仍用于供应商可用性，真实 usage 只在 Pi 能提供可靠事件时用于用户体验效率。原型先行，但原型只作为版本化设计产物，不接入生产数据。

## Goals / Non-Goals

**Goals:**

- 用同一时间范围和同一聚合口径提供消费结构、项目归因和 provider/model 排行。
- 在可靠真实时间点存在时，提供有样本门槛的 p50/p95 延迟和成功率。
- 生成成本、效率、缓存三个维度的只读建议，并暴露建议依据。
- 用独立原型先验证页面的信息层级、数据态和窄视口布局。
- 保持本地优先、无新外部服务、旧 SQLite 可迁移和基础统计可降级。

**Non-Goals:**

- 不实现自动模型路由、自动修改配置或自动供应商切换。
- 不把 probe 延迟混入真实调用效率排行。
- 不引入质量评分、用户反馈、社区基准或预测模型。
- 不引入 ClickHouse、Prometheus、OpenTelemetry collector 或外部遥测后端。
- 不在本变更中重做账户、诊断和供应商 probe 的既有功能。

## Decisions

### 1. SQLite 原始事件 + 服务端聚合

继续使用现有 `usage_records`，增加可选真实调用时间点和结果状态列，并在 Database 层增加受限聚合查询。API 返回完成计算的指标和洞察，前端只负责展示。

选择原因：现有数据量与本地扩展场景不需要新的分析数据库；服务端统一口径可以保证总览、排行、归因和建议一致；聚合结果可设置上限，避免把无限明细发送到浏览器。

替代方案：前端读取原始记录后计算被拒绝，因为会暴露更多数据、增加重复逻辑，并容易造成四舍五入或时间范围口径不一致。

### 2. 真实调用延迟和 probe 延迟分离

新增真实调用延迟字段只接受 Pi 事件链中可验证的开始、首字和结束时刻。probe 继续写入 `probe_records`，不参与真实 usage 效率推荐。

选择原因：固定 `hi` probe 的网络和请求形态不能代表用户真实上下文；混合两者会让“最佳模型”结论失真。缺失时间点时保留 NULL，基础 tokens/费用照常记录。

替代方案：用 `message_end - 上一条记录` 或 probe 数据补齐被拒绝，因为无法证明其对应同一次调用。

### 3. 使用稳健统计和最小样本门槛

效率排行使用 p50/p95，而不是平均值；成本与效率建议仅使用达到最低样本阈值的组合。第一版将最低样本阈值固定为 10，后续若有证据再配置化。

选择原因：p50 表示典型体验，p95 反映长尾；固定门槛减少“为每个规则建配置”的复杂度，并防止单次偶然调用成为推荐。

### 4. 建议是解释层，不是决策执行层

洞察生成器只接受已聚合的统计，输出维度、对象、依据、样本数、时间范围和置信度。它不能调用配置写入或模型选择路径。

选择原因：当前没有质量数据，不能生成无条件的“最佳模型”；只读建议能提供价值，同时保持用户对配置和成本的控制。

### 5. 原型使用独立版本化产物

先在 `.pi/prototype-design/<project>/` 产出总览原型，至少验证桌面、窄视口、有数据、无数据、样本不足和延迟不可用状态。通过评审后再修改生产 UI。

选择原因：当前 dashboard 页面由多个原生 DOM 片段拼装，直接调整首屏层级容易造成回滚范围扩大；版本化原型可以先确认信息架构。

### 6. 保持单次 dashboard 请求

第一版继续扩展 `/api/dashboard` 返回 `efficiency`、`insights`、`cache` 等有界字段，而不是增加多个串行请求；若返回体经过实际测量超出合理范围，再拆分独立接口。

选择原因：当前页面已有同一时间范围的统一刷新和并发请求保护，继续单请求能保持状态简单。排行和趋势都应限制数据点/行数。

### 7. 成品视觉采用 shadcn base 的 CSS 移植

成品面板不引入 React 与构建步骤：把 shadcn base 组件（Card/Badge/Tabs/Button/Skeleton/Separator 等）的默认视觉用仓库既有的 shadcn oklch CSS token 在 `dashboard-css.ts` 实现，含 focus ring、交互状态与加载骨架；零新依赖、零外部资源。

选择原因：面板是无构建内联脚本 + 原生 DOM，且存在零 `<script src=` 外部引用测试；shadcn base 底层 Base UI 为 React-only，直接引入违反现行约束。

替代方案：引入 React + 构建管线被否——需改写整个 dashboard client 并修改仓库约束，范围大幅扩大；先做 hifi 再定被否——CSS 移植可独立回滚且视觉等价，无需多一轮评审。

## 原型评审结论（2026-09-22 已固定）

- **信息层级（两轮评审通过）**：成品壳 = range 四档前置于标签栏 + 四标签（总览/统计/趋势/供应商，data-tab-panel 切换）；总览面板内 P0 五指标（auto-fit 网格，含缓存命中率）→ P1 解释型建议 → P2 排行摘要（三列小表，完整口径在统计标签）；消费趋势在趋势标签。
- **建议卡片布局**：纵向堆叠，结论行在上，其下依次为依据、样本数、时间范围、置信度。
- **未采纳的复杂图表/交互**：tooltip 悬浮数值、堆叠面积图、图表缩放/拖拽——首版不实现，亦不列入本变更范围。
- **范围确认**：本变更 capability 边界不变；shadcn base 视觉移植只是 4.1 的实现方式约束（见决策 7），不新增能力章节、不扩大范围。

## Risks / Trade-offs

- [Pi 事件不提供可靠时间点] → 保留基础消费统计，效率模块显示暂无数据；不使用估算值。
- [SQLite 聚合查询变慢] → 使用时间、provider/model 索引，限制排行和趋势结果数量，并用测试数据验证查询耗时。
- [建议被误读为质量结论] → 文案明确“基于成本/延迟/缓存”，展示样本和时间范围，不使用无依据的综合最佳表述。
- [旧数据库缺少新增列] → 使用现有幂等 schema migration，旧记录字段保持 NULL，补充迁移测试。
- [原型与生产实现出现偏差] → 原型明确示例数据和未接入状态；生产实现前以原型评审结果更新 tasks，不把原型代码当生产代码复用。
- [页面信息过密] → 首屏只展示有限排行，次要组合折叠/汇总；先通过原型评审验证视觉层级。
- [延迟空值和失败请求混淆] → 分开表示“无可靠数据”“样本不足”和“失败率”，不把 NULL 转换成 0。

## Migration Plan

1. 创建并评审使用量总览原型；原型不写入生产数据库或生产路由。
2. 在测试数据库上增加可选真实延迟和结果状态列，验证旧库打开、重复迁移和旧记录查询。
3. 先发布消费结构与项目排行字段，保持既有 API 字段兼容。
4. 若 Pi 事件支持可靠时间点，再启用真实效率采集与聚合；否则仅发布明确空态。
5. 发布解释型建议，建议字段缺失时降级，不影响基础 dashboard。
6. 回滚时移除新 UI 区块或停止读取新字段即可；保留新增 NULL 列和历史记录，不要求删除数据库。必要时恢复旧 dashboard 响应映射，既有字段保持兼容。
