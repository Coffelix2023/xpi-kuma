# ADR 0001：xpi-kuma 的进程边界与所有权划分

状态：已接受 · 日期：2026-09-14 · 关联变更：`openspec/changes/add-standalone-service-daemon/`

## 背景

README「进程边界」一节要求：扩展是 Pi 主进程内的插件，不是独立服务；确需进程边界时，先写 ADR 说明理由再动手。本变更引入独立守护进程（终端启动、脱离 Pi 存活），正是第一次真正跨进程，因此按约定记录边界。

当前事实：

- 网页仪表盘（`src/ui/dashboard.ts`）与供应商探测定时器（`src/monitors/vendor-monitor.ts`）挂在 Pi 进程内的运行时上，Pi 退出即消失。
- 真实用量采集（`message_end` → `UsageCollector` → SQLite）同样只在 Pi 进程内有意义——它消费的是 Pi 的事件。
- 扩展缺席期间（扩展未加载、Pi 内服务被关闭、旧版本无扩展），真实调用的 token 与费用已持久化在 Pi 会话 JSONL 日志（`<agentDir>/sessions/<项目>/*.jsonl`）里，但没有机制补入 `usage.db`。

## 决策：三个所有权角色

### 1. Pi 实时采集（recorder）——永远属于 Pi 进程

只要 Pi 会话存活，扩展就持续监听 assistant `message_end` 并写入共享 `usage.db`。这与网页/探测的开关**彻底解耦**：`/xpi-kuma off` 只停网页与探测，不停采集器与数据库连接。

对应 spec：`usage-collection`「真实用量采集独立于网页服务开关」两个 scenario；`dashboard-ui`「off 关闭不阻塞 Pi」。

理由：采集依赖 Pi 进程内的事件流，天然无法外移；把它和服务开关绑在一起只会在用户关面板时静默丢失数据。

### 2. 共享补录（reconciler）——Pi 与独立服务共用的同一模块

同一套「扫描 Pi 会话日志 → 幂等补入数据库 → 与已实时记录的行对账」逻辑，分别在两个时机运行：

- Pi `session_start`（保留期清理之后，扫描下界与清理截止时间一致）；
- 独立服务 `on`（首次网页查询之前）。

并发触发靠数据库唯一约束（`(session_id, source_entry_id)` 唯一索引）保证只入账一次；指纹冲突、旧行不可判定时显式报告「未核实」，不猜、不双计。补录行不推断延迟字段。

对应 spec：`usage-collection`「从 Pi 会话日志幂等补录缺失用量」全部 scenario；`standalone-service`「服务就绪且首次网页查询前执行共享的幂等日志补录」。

理由：两个入口必须看到同一条幂等规则，否则任何一方独立实现都会在重叠日志上重复计数。

### 3. 独立网页与探测（service owner）——可由独立进程持有，单方所有

网页监听与供应商探测定时器在同一时刻只允许一个所有者：Pi 进程内运行时，或独立守护进程。独立服务存在时，Pi 复用其 URL、不启动第二个监听器与探测组；Pi 已先启动时，独立 `on` 明确报告冲突而不是悄悄接管。

对应 spec：`standalone-service`「独立服务单实例与安全进程协调」「与 Pi 扩展共享网页和探测所有权」；`dashboard-ui`「独立服务持有网页」；`vendor-monitoring`「独立服务先运行」。

理由：两个 HTTP 监听器会端口冲突，两组探测定时器会重复请求供应商并污染统计；所有权必须单方、可校验、可让渡。

### 明确不做

- 内容摘要**不落库**：对账指纹由会话、消息时间、供应商/模型、token 与费用字段构成；摘要只在两端都有且候选相同时辅助消歧，不作为基础键，schema 也没有对应列。
- 补录无法核实的条目不会被宣称为已补齐；「零断档」不承诺。
- 独立服务不做系统服务管理器集成、开机自启、远程监听。

## 后果

- 新增终端命令 `xpi-kuma on/off/status` 与后台进程生命周期（daemon 实现、进程协调、宿主终端隔离见后续任务的实现）。
- `usage_records` 需要向前迁移：可空来源条目 ID、消息时间、对账指纹列及唯一索引；存量行为不变。
- Pi 内 `off` 语义收窄为「停网页与探测」；`session_shutdown` 行为不变（服务跨会话常驻，采集随 Pi 存活）。
- 回滚：停止 daemon、移除命令入口、恢复 Pi 侧所有权即可；新增列与历史数据保留，不做逆向删除。
