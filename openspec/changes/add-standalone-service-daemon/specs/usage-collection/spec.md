## ADDED Requirements

### Requirement: 真实用量采集独立于网页服务开关
Pi 扩展 SHALL 在 Pi 会话存活期间持续监听并记录有效的 assistant `message_end` usage，不论仪表盘/探测服务是否开启、由独立进程拥有或启动失败。用户关闭网页/探测服务 MUST NOT 停止实时用量采集。

#### Scenario: 服务关闭期间 Pi 继续调用模型
- **WHEN** 用户已关闭网页和探测服务，但 Pi 会话仍运行并完成带 usage 的 assistant 调用
- **THEN** 系统将该调用写入共享 usage 数据库且只写入一次

#### Scenario: 独立服务拥有仪表盘期间 Pi 继续调用模型
- **WHEN** 独立服务持有仪表盘和探测所有权，Pi 会话收到带 usage 的 `message_end`
- **THEN** Pi 扩展仍记录真实用量，且不启动第二组供应商探测

### Requirement: 从 Pi 会话日志幂等补录缺失用量
系统 SHALL 在 Pi 会话启动时以及独立服务启动时检查可读取的 Pi 持久会话日志，并将保留期内、此前未记录且身份可判定的 assistant usage 补入共享 usage 数据库。两个入口同时运行也 MUST 只入账一次。补录 SHALL 用日志条目身份保证重扫幂等，并用稳定指纹与已实时记录的行对账；指纹冲突、旧行缺少足以对账的字段或日志不可读时，系统 MUST 保留既有数据、跳过无法判断的条目并提供未核实数量与定位，MUST NOT 把未核实条目宣称为已补齐。补录记录的请求开始、首 token 和完成延迟 SHALL 保持未知，除非原始记录直接提供可信时间点。

#### Scenario: 补录扩展缺席期间的会话记录
- **WHEN** Pi 会话日志含有保留期内的 assistant usage，而数据库中没有其对应记录
- **THEN** 会话启动时补入该条 token、费用、供应商、模型、会话和项目归因信息

#### Scenario: 独立服务启动时补录
- **WHEN** 用户执行 `xpi-kuma on` 且 Pi 未运行，会话日志中有保留期内未入库的 assistant usage
- **THEN** 服务启动过程补入可识别记录，网页首次加载即包含这些用量

#### Scenario: 双入口并发补录
- **WHEN** Pi 会话启动与 `xpi-kuma on` 几乎同时触发补录
- **THEN** 每个日志条目仍只入账一次，不产生重复行或因冲突导致的失败退出

#### Scenario: 日志条目可稳定识别且不与已有记录冲突
- **WHEN** 同一 Pi 会话日志被重复扫描，条目具有稳定 id，且与已有实时记录的指纹能唯一对账
- **THEN** 每个条目仅贡献一次统计；已实时记录的调用不得再次插入

#### Scenario: 指纹冲突或旧行不可核实
- **WHEN** 相同指纹有多个候选，或旧数据库记录缺少对账所需字段，无法确认某条日志是否已入账
- **THEN** 系统不自动插入该条，保留已有数据并报告未核实数量和日志位置
#### Scenario: 补录记录不推断延迟
- **WHEN** 日志 usage 不包含可信的请求开始或首 token 时间点
- **THEN** 补录行的对应延迟字段保持 NULL，统计不把未知显示成零延迟

#### Scenario: Pi 完全未运行
- **WHEN** Pi 已关闭且期间没有 Pi 调用产生会话日志记录
- **THEN** 系统不伪造使用量；若 Pi 曾在扩展未采集时运行并写下日志，则之后 Pi 会话启动或独立服务 `xpi-kuma on` 时可补录其可识别记录
